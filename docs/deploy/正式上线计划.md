# MHTT 正式上线计划

版本 v2.1 · 2026-11-10

> **本仓库只管 MHTT。** 2026-11-10 起 MHTT 和 AIIS 是两套独立的代码（两个 GitHub 仓库），之后各自修改、互不同步。本计划从 AIIS 仓库的上线计划 v1.4 拆出，只保留 MHTT 的部分；AIIS 的计划在 AIIS 仓库里。

本计划把之前分散在各处的上线决定汇总到一起：设计文档 §6.7.7–6.7.8、README、云资源需求文档、演示文稿 *AIIS ERP Design and Cloud Trial* 第 9–10 页。业务规则仍以 [审批流程设计.md](../design/审批流程设计.md) 为准，本文件只管“怎么上线”。

## 1. 部署方式

**MHTT 用自己的一套代码、一台云服务器、一个库，和 AIIS 完全隔离。**

| | MHTT |
|---|---|
| 代码 | 本仓库（从 AIIS 代码 2026-11-10 的版本复制出来，之后独立修改，不和 AIIS 同步） |
| 服务器 | 云上一台新服务器 |
| 数据库 | 一个库 `mhtt`，只放 MHTT 的数据 |
| 系统 | 全新安装，不带演示数据；试用只录新数据（见第 6 节） |
| 域名、备份存储、LDAP、管理员账号 | MHTT 自己的一套 |

- 和 AIIS 没有任何共用的东西：不共用代码、数据库、存储、账号，也不互相连接。
- MHTT 和 AIIS 不同的需求直接改本仓库的代码，不必为了兼容 AIIS 做成配置开关。模块技术名暂时保留 `aiis_*`（界面上看不到），界面上的名称已改为 MHTT。
- 不用 Odoo 自带的多公司功能。
- **内网开发服务器**上有一套 MHTT 的开发环境（容器 `mhtt-app` / `mhtt-db`，端口 8169，库 `mhtt`，不带演示数据），和 AIIS 的测试环境并排运行、互不影响。真实数据不导进开发库。

**阶段：**

| 阶段 | 内容 | 结束标志 |
|---|---|---|
| A. 云上试用 | 按第 5 节部署，用真实数据试用一个月 | M4：CEO 签字同意转正式 |
| B. 转正式 | 试用库直接转为正式库，数据保留，不重建 | 开启长期备份和监控 |

## 5. 部署步骤

按下表部署。天数从云服务商交付服务器那天算起。

| 步骤 | 时间 | 做什么 | 谁做 | 检查 |
|---|---|---|---|---|
| 1 | 第 0 周 | 选定云服务商，签合同；第 2 节的事项全部定下来 | 你 | 第 2 节没有空项 |
| 2 | 第 1 天 | 服务器：Ubuntu、Docker、防火墙、域名指向、HTTPS 证书（Caddy 自动申请）、VPN | 开发 + IT | 浏览器打开域名显示 HTTPS 锁 |
| 3 | 第 2 天 | 应用：见下方“应用配置” | 开发 | 登录正常，通知能实时弹出 |
| 4 | 第 2 天 | 全新安装：`deploy/first_install.sh`，新库不带演示数据，**先装沙特科目表 `l10n_sa`，再装本仓库的模块**（有了凭证之后科目表就不能换了）；然后用 `scripts/setup_company_brand.py` 设置 Logo、深蓝主题色和公司全称 | 开发 | 科目表是沙特版；本位币 SAR；登录页是 MHTT 的 logo |
| 5 | 第 3–4 天 | 导入本公司的真实数据：部门、员工和上下级、用户、CEO / Chairman / CFO 职位、供应商、客户、产品、预算；在公司设置里选研发部门、采购部门 | 开发 + 各数据负责人 | `scripts/post_import_check.py` 没有需要修复的项 |
| 6 | 第 4 天 | 备份：定时任务启动；把备份拷到开发服务器，完整恢复一次 | 开发 | 恢复出来的库能登录，数据对得上 |
| 7 | 第 5 天 | 试运行：关键用户把每条流程从头走到尾；通过后给全员发账号 | 关键用户 | 第 9 节的流程全部走通 |

**应用配置（第 3 步）：**

以下各项已经写进 `deploy/` 里的配置和脚本，具体命令见 [`deploy/README.md`](../../deploy/README.md)。

- 多进程：`workers` 4，`max_cron_threads` 1–2，同时设内存上限（`limit_memory_soft/hard`）和时间上限（`limit_time_cpu/real`）。每个进程约占 150–300 MB 内存。
- Odoo 和数据库不映射任何端口（Docker 映射出来的端口会绕过防火墙），只有 Caddy 对外开放 80/443：`/websocket` 转到 8072，其余转到 8069。
- `proxy_mode = True`，`list_db = False`。服务器上只有一个库，`dbfilter` 固定为 `^mhtt$`；不写 `db_name`（否则 Odoo 第一次启动就会自己建库）。
- 管理员密码（`admin_passwd`）、数据库密码换成强密码，和 AIIS 的**不同**，由 `deploy/.env` 注入。
- 配置 MHTT 的发信服务器，确认通知邮件能发出去。
- 员工登录：按第 2 节第 3、4 项，LDAP / AD 放入根证书并运行 `scripts/setup_ldap.py`；Microsoft 365 / Google 配置 OAuth 登录。

账号只在 MHTT 的服务器上；同一个人在 AIIS 也有账号时，两边分别开、分别管。

| 账号 | 用途 | 要求 |
|---|---|---|

## 8. 备份、升级与测试

**三份拷贝：**

| 频率 | 内容 | 存放位置 |
|---|---|---|
| 每 4 小时 | 数据库 + 附件 | 本公司的云备份存储（另一个可用区） |
| 每天 | 服务器整机快照 | 云服务商 |
| 每晚 | 数据库 + 附件 | 通过 VPN 拷回本公司办公室 |

- 用 `scripts/backup.sh` 生成备份，正式库开启定时任务。目前内网测试库没有开自动备份。
- **每次发布前**先手动备份一次。
- 每月至少在开发服务器上完整恢复一次，证明备份确实能用。

**代码升级不丢数据：** Odoo 升级模块时会保留已有数据；字段或结构有变化时，由模块里的升级脚本把旧数据转换成新格式。

**发布流程：**

1. 员工报告问题，我们在开发服务器上修复，先在开发库 `mhtt` 通过自动化测试，再跑 `scripts/fresh_install_check.sh`（证明还能全新安装）；
2. 把 MHTT 最新的备份经 SSH 加密拷到开发服务器，恢复成一个临时库，升级并测试；
3. 测完**删掉临时库和拷贝**；
4. 云上正式库先备份，再升级，然后重启。

**真实数据放到开发服务器上的规矩：**
- 只放在开发服务器上，不拷到个人电脑；
- 只恢复 MHTT 的数据，用完就删；
- 恢复出来的临时库不发邮件，不运行定时任务（启动时设 `--max-cron-threads=0`，并关闭发信）；
- 开发服务器只在内网访问。

试用期间每周发布两次，紧急问题可以随时发布。

- [ ] 没有未解决的严重问题
